    [참고] Kubernetes essentials¶

    이 문서의 역할

    2일차 AKS Lab(Lab 90~Lab 92) 전에 Kubernetes 핵심 용어와 구조를 한 페이지로 훑습니다. 실습에서 직접 만나는 개념 위주로 정리했으며, 깊이 있는 내용은 공식 문서를 참고하세요.

    Container & Kubernetes 참고

    • Container basics: https://noisonnoiton.github.io/blogs/004_cna/container/
    • Kubernetes basics: https://noisonnoiton.github.io/blogs/004_cna/k8s/

    1. 인프라 진화 — 서버에서 오케스트레이션까지¶

    단계 특징 비유
    Physical Server 1 앱 = 1 장비 단독 주택
    Virtual Machine 1 장비에 여러 OS 아파트
    Container 경량, 빠른 시작 공유 오피스
    Kubernetes 컨테이너 자동 관리 건물 관리자

    컨테이너는 패키징을 해결하고, Kubernetes는 대규모 운영을 해결합니다.

    2. Kubernetes란?¶

    Kubernetes(K8s)는 컨테이너화된 애플리케이션의 배포, 스케일링, 자동 복구를 관리하는 오픈소스 플랫폼입니다.

    항목 내용
    유형 Open Source (CNCF)
    카테고리 Container Orchestrator
    기원 Google Borg → 2014 공개
    약칭 K8s (K와 s 사이 8글자)

    핵심 원칙 — Declarative(선언적):
    "원하는 상태(desired state)"를 YAML로 정의하면, Kubernetes가 현재 상태를 원하는 상태로 수렴시킵니다.

    3. Architecture¶

    Kubernetes 클러스터는 크게 Control Plane(관리)과 Worker Node(실행) 두 영역으로 나뉩니다.
    먼저 전체 구조를 보고, 각 구성요소를 세부적으로 살펴본 뒤, 네트워크 계층과 애플리케이션 흐름을 이해합니다.

    3-1. 클러스터 구조 (Control Plane + Worker Node)¶

    아래 다이어그램은 사용자가 kubectl 명령을 내리면 클러스터 내부에서 어떤 일이 일어나는지를 보여줍니다.

    Control Plane (마스터)¶

    클러스터의 두뇌 역할을 합니다. 사용자 요청을 받아 어디에 무엇을 배치할지 결정하고, 현재 상태를 desired state로 유지합니다.

    Component 역할
    API Server 모든 요청의 진입점 (kubectl 명령 수신)
    etcd 클러스터 상태를 저장하는 Key-Value DB
    Scheduler 새 Pod을 어느 노드에 배치할지 결정
    Controller Manager desired state ↔ current state를 지속 비교·조정

    AKS에서는

    Control Plane은 Azure가 관리합니다. etcd에 직접 접근하거나 마스터 노드에 SSH 할 수 없으며, kubectl로만 상호 작용합니다.

    마스터에 Pod 배포가 가능한가?

    기술적으로 마스터 노드에도 kubelet이 있으므로 Pod 실행이 가능합니다.
    다만 기본 설정에서 Taint(node-role.kubernetes.io/control-plane:NoSchedule)로 사용자 워크로드가 스케줄되지 않도록 방지합니다.
    AKS처럼 매니지드 서비스에서는 마스터에 접근 자체가 불가능하므로 Pod 배포 대상은 Worker Node만 됩니다.

    Worker Node¶

    실제로 컨테이너(Pod)가 실행되는 일꾼 노드입니다.

    Component 역할
    kubelet API Server 지시를 받아 Pod/컨테이너 실행
    kube-proxy Service 네트워킹 규칙 관리 (iptables/IPVS)
    Container Runtime 실제 컨테이너 실행 (AKS는 containerd 사용)

    AKS Node Pool

    Lab 90에서 system pool(1 node) + user pool(1 node)을 생성합니다. VMSS 기반이며 kubectl get nodes로 확인합니다.

    3-2. 네트워크 계층 (Underlay + Overlay)¶

    Kubernetes 클러스터에는 3개의 네트워크 계층이 겹쳐서 동작합니다. 아래 그림에서 각 계층의 역할을 확인하세요.

    계층 CIDR 예시 역할
    Underlay (물리/VM) 210.100.0.x 노드 간 실제 통신에 사용되는 물리 IP (Azure VNet의 NIC IP)
    Pod Network (overlay) 172.10.0.0/16 각 Pod에 고유 IP 부여 — Pod 간 직접 통신
    Service Network (virtual) 10.10.0.0/16 Service의 ClusterIP — kube-proxy가 Pod으로 포워딩
    • 모든 노드(Master 포함)는 Underlay 네트워크에 연결됩니다
    • Worker 노드는 추가로 Pod Network와 Service Network에 참여하여 실제 워크로드 트래픽을 처리합니다
    • Control Plane도 내부적으로 Pod/Service 네트워크와 통신하지만, AKS에서는 Azure가 관리하는 별도 VNet에 위치합니다

    CNI 플러그인

    Pod Network의 구현은 CNI(Container Network Interface) 플러그인이 담당합니다.
    AKS에서는 Azure CNI Overlay 또는 kubenet을 선택할 수 있으며, Lab 90에서는 Azure CNI Overlay를 사용합니다.

    3-3. 논리적 오브젝트 흐름 (트래픽 관점)¶

    인프라를 이해했으니, 이제 사용자 요청이 클러스터 안에서 어떻게 흘러가는지 논리적 오브젝트 관점에서 봅니다.

    트래픽 흐름: User → Ingress(L7 라우팅) → Service(로드밸런싱) → Pod(실제 앱 컨테이너)
    관리 흐름: Deployment가 Pod의 생명주기를 관리하고, PVC/PV로 스토리지를, ConfigMap으로 설정을 분리합니다.

    [참고] 3-4. Container Runtime 표준 — OCI와 containerd¶

    Worker Node에서 Pod을 실행하는 마지막 단계가 Container Runtime입니다.
    Docker는 컨테이너를 대중화한 도구이지, 표준이 아닙니다. 실제 표준은 OCI(Open Container Initiative) 입니다.

    계층 구성요소 역할
    표준 규격 OCI Image Spec 이미지 레이어 포맷 정의 (docker pull로 받는 그것)
    표준 규격 OCI Runtime Spec 컨테이너를 어떻게 실행하는지 정의
    런타임 (고수준) containerd 이미지 pull, 저장, 컨테이너 생명주기 관리 (CNCF, AKS 기본)
    런타임 (저수준) runc OCI Runtime Spec을 실제로 구현 — 컨테이너를 실행하는 최하단
    K8s 인터페이스 CRI kubelet ↔ 런타임 간 표준 통신 인터페이스 
    kubelet
  └─ CRI (Container Runtime Interface)
       └─ containerd  ← AKS가 사용하는 런타임
            └─ runc   ← OCI Spec 구현체, 실제 프로세스 격리
                 └─ container (실행 중인 프로세스)
    • Docker는 개발자 UX 도구 (docker build / docker run) — 내부적으로 containerd를 사용
    • Docker가 만든 이미지 포맷이 OCI Image Spec으로 표준화됨 → docker build 결과물은 OCI 호환
    • Kubernetes 1.24+에서 dockershim 제거 → kubelet이 containerd와 CRI로 직접 통신
    • 개발 시 docker build한 이미지를 AKS에 올려도 문제없는 이유: 둘 다 OCI Image Spec 준수

    정리

    개발 PC에서 docker run으로 테스트하고, 프로덕션 AKS에서 containerd + runc로 실행합니다.
    이미지 포맷(OCI)이 동일하기 때문에 가능합니다.

    4. Core Objects¶

    Pod¶

    • Kubernetes의 최소 배포 단위
    • 보통 1 Pod = 1 Container (가장 흔한 패턴)
    • Pod 안 컨테이너끼리 네트워크(같은 IP, localhost 통신)와 스토리지를 공유
    • Pod은 임시(ephemeral) — 죽으면 새로 생성 (IP 변경)

    Namespace¶

    클러스터를 논리적으로 격리하는 단위입니다.

    kubectl get namespaces
    Namespace 용도
    default 기본
    kube-system K8s 핵심 컴포넌트 (CoreDNS, Metrics Server, kube-proxy 등)
    app-routing-system AKS Web App Routing (NGINX Ingress Controller)

    Lab 91에서

    마이크로서비스를 awesome, awesome-infra 등 별도 namespace에 배포합니다.

    Label & Selector¶

    • Label: 리소스에 붙이는 key=value 태그 (예: app=nginx)
    • Selector: Label을 기준으로 리소스를 쿼리 (Service가 Pod을 찾는 방식)

    5. Workloads¶

    Type 용도 Lab 연결
    Deployment Stateless 앱 (Web, API) — ReplicaSet 자동 관리 Lab 91 마이크로서비스 전체
    StatefulSet 순서·고유 ID 필요 (DB, 메시지 큐) Lab 91 MySQL, RabbitMQ
    DaemonSet 모든 노드에 1개씩 (모니터링 agent, 로그 수집) Lab 92 OTel Collector
    Job / CronJob 1회·주기적 배치 작업 (이 과정에서는 직접 사용하지 않음)

    Deployment → ReplicaSet → Pod

    Deployment를 만들면 K8s가 자동으로 ReplicaSet을 생성하고, ReplicaSet이 지정된 수만큼 Pod을 유지합니다. replicas: 3이면 항상 3개 Pod이 Running 상태를 유지합니다.

    6. Service & Ingress¶

    Service Type 노출 범위 사용 예
    ClusterIP 클러스터 내부만 서비스 간 통신 (DB → App)
    NodePort 노드 IP:포트 테스트용 (프로덕션 비권장)
    LoadBalancer 외부 IP (Azure LB 자동 생성) Lab 91 API Gateway 외부 노출
    ExternalName 외부 DNS 매핑 외부 SaaS 연결

    Ingress¶

    • L7(HTTP/HTTPS) 라우팅 — Host, Path 기반으로 여러 Service에 트래픽 분배
    • AKS에서는 Web App Routing add-on이 NGINX Ingress Controller를 자동 배포
    • IngressClass: webapprouting.kubernetes.azure.com

    Lab 91에서

    Ingress를 통해 <EXTERNAL-IP>.nip.io host-based routing으로 서비스를 외부 노출합니다.

    DNS — CoreDNS¶

    클러스터 내 DNS 요청은 CoreDNS가 처리합니다. kube-system 네임스페이스에 Deployment로 실행되며, Service에 자동 DNS 이름을 부여합니다.

    # CoreDNS 확인
kubectl get pods -n kube-system -l k8s-app=kube-dns

    Service는 아래 패턴의 DNS 이름을 자동으로 부여받습니다:

    <service-name>.<namespace>.svc.cluster.local
    예시 해석
    mysql.awesome-infra.svc.cluster.local awesome-infra 네임스페이스의 mysql 서비스
    redis.awesome-infra.svc.cluster.local awesome-infra 네임스페이스의 redis 서비스

    같은 Namespace 내 통신

    같은 Namespace 안에서는 서비스 이름만으로 통신 가능합니다.
    mysql.awesome-infra.svc.cluster.local 대신 mysql만 써도 됩니다.

    7. Storage & Configuration¶

    Storage¶

    개념 역할
    Volume Pod에 마운트되는 저장소 (Pod 삭제 시 소멸 가능)
    PersistentVolume (PV) 클러스터 수준의 영구 스토리지
    PersistentVolumeClaim (PVC) Pod이 PV를 요청하는 방법
    StorageClass 동적 프로비저닝 규칙 (AKS: managed-csi = Azure Disk)

    Lab 91에서

    MySQL, RabbitMQ가 PVC를 사용하여 Azure Managed Disk에 데이터를 영구 저장합니다.

    ConfigMap & Secret¶

    Object 용도
    ConfigMap 비민감 설정 (DB host, feature flag)
    Secret 민감 데이터 (password, API key) — base64 인코딩

    Health Probes¶

    Probe 역할
    Liveness 죽었으면 재시작
    Readiness 준비 안 됐으면 트래픽 차단
    Startup 초기화 완료까지 다른 probe 지연

    8. Scaling¶

    • 트래픽이 늘면 같은 Pod에 컨테이너를 추가하는 것이 아니라, Pod 수를 늘립니다 (Horizontal Scaling)
    • 노드가 부족하면 새 노드를 추가합니다 (Cluster Autoscaler)
    방식 대상 설명
    HPA (Horizontal Pod Autoscaler) Pod CPU/Memory 기준 Pod 수 자동 조정
    VPA (Vertical Pod Autoscaler) Pod 개별 Pod의 resource request/limit 조정
    Cluster Autoscaler Node 노드 수 자동 조정 (AKS에서 지원)

    10. kubectl Cheatsheet (Lab에서 쓰는 명령)¶

    명령 설명
    kubectl get nodes 노드 목록
    kubectl get pods -A 전체 namespace Pod 조회
    kubectl get svc Service 목록 (External IP 확인)
    kubectl get namespaces Namespace 목록
    kubectl describe pod <NAME> Pod 상세 (Events, Conditions)
    kubectl logs <POD> Pod 로그 확인
    kubectl top nodes 노드 CPU/Memory 사용량
    kubectl top pods -A Pod CPU/Memory 사용량
    kubectl get events --sort-by='.lastTimestamp' 최신 이벤트
    kubectl apply -f <FILE> 선언적 리소스 생성/업데이트
    kubectl apply -k <DIR> Kustomize 기반 배포
    kubectl delete -f <FILE> 리소스 삭제
    kubectl exec -it <POD> -- bash Pod 내부 셸 접속
    kubectl rollout undo deploy <NAME> 이전 버전 롤백
    kubectl scale deploy <NAME> --replicas=N 수동 스케일링
